Jersey OCR Flow: 6 Phases

Phase 1 - Video upload and job creation
- User uploads a video through POST /api/videos/upload with team_id.
- The API creates a VideoJob row in the database.
- A background task starts video processing asynchronously.

Phase 2 - Frame reading and video processing setup
- process_video_job() opens the uploaded video file.
- VideoProcessor computes the frame interval using native FPS and target FPS.
- A ByteTrack tracker is initialized to keep a stable track_id for each player across frames.
- The processor loops through the video frame by frame.

Phase 3 - Player detection and tracking
- YOLODetector.detect_players() runs on each sampled frame.
- The detector keeps only person detections and filters out small boxes.
- ByteTrack.update() assigns track_id values so the same player can be followed across frames.
- The output of this phase is a list of tracked player detections with bounding boxes and confidence scores.

Phase 4 - Jersey crop preprocessing and OCR
- For each tracked detection, the player bounding box is padded slightly.
- The crop is extracted from the frame and checked for minimum size.
- The crop is resized to a target height while keeping aspect ratio.
- The image is enhanced with grayscale conversion, CLAHE, Gaussian blur, and sharpening.
- JerseyRecognizer then tries OCR using PaddleOCR.
- It tests multiple image variants: base, otsu, inverted_otsu, and adaptive.
- The OCR result is parsed to extract digits only.
- If a numeric jersey is found with enough confidence, it is accepted.
- If not, the recognizer records a reason such as crop_too_small, low_confidence, no_text_or_digits, or ocr_failure.

Phase 5 - Persistence into detection_frames
- Each detection is stored in detections_json inside a DetectionFrame row.
- The payload includes class_id, class_name, confidence, track_id, bbox, jersey_number, jersey_confidence, jersey_ocr_status, and jersey_ocr_reason.
- Frames are committed to the database periodically while processing continues.
- This is the place where OCR output must appear if recognition is working.

Phase 6 - Player mapping from saved detections
- The endpoint POST /api/videos/{job_id}/player_mapping/auto?team_id={team_id} reads the saved detection frames.
- If recompute_from_frames=true is passed, OCR is run again from stored frame crops before mapping.
- PlayerMapper.aggregate_jerseys_from_video() groups detections by track_id.
- It computes confidence statistics and chooses the most likely jersey number per track.
- It matches the detected jersey number to players on the team roster.
- The final result is a PlayerMappingResponse with mapping suggestions and confidence ratings.

Important debugging checkpoints
- If jersey_number is always null, the failure is usually in OCR or preprocessing.
- If jersey_ocr_reason is missing, the running API may not be using the updated code path.
- If detection frames exist but mapping is zero, the save or recompute path may be the problem.
- If the OCR reason shows crop_too_small, the detection box is likely too small or cut off.
- If the OCR reason shows low_confidence, the crop exists but the OCR result is too weak to trust.
- If the OCR reason shows failure, an exception happened during OCR or preprocessing.
